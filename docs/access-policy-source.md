# Native access policy file delivery

[简体中文](access-policy-source.zh-CN.md) | English

This optional deployment supplies the static HTTPS source expected by the
native access Operator in
[PR #356](https://github.com/rongxinzy/Agent-Enterprise-Protocol/pull/356).
It can be reviewed/merged independently; install the writer before sending
model traffic to this source. It does not enable Authorino, configure Higress,
change the default authorizer, publish DB authorization or assert fleet adoption.

## Components and trust

The deployment uses existing upstream software, not a custom policy server:

- [kiwigrid/k8s-sidecar 2.14.1](https://github.com/kiwigrid/k8s-sidecar/tree/2.14.1),
  source revision `ea5578d71554967babd90d6eb7e244daa5688a71`, watches only
  ConfigMaps labeled `gateway.aep.zhiyuan.io/access-policy=true` in `aep-system`
  and materializes their files into each Pod's emptyDir.
- [nginx-unprivileged 1.30.2-alpine](https://github.com/nginx/docker-nginx-unprivileged)
  serves only `/access-<64 lowercase hex>.rego` over TLS. Policy storage is
  read-only to Nginx, directory listing is off, mutation methods are denied,
  HTTP caching is disabled and request access logging is off.

Both images are pinned by their actual registry index digests in the manifest.
There is no new Dockerfile, evaluator, authorization cache or DB writer. The
sidecar copies bytes; it does not interpret Rego, verify its publication or
rewrite its absolute deadline. The existing Operator owns the files' meaning.

The separate service account can only get/list/watch ConfigMaps in `aep-system`.
Kubernetes RBAC cannot restrict list/watch to a label: this identity can read
other ConfigMaps in that namespace, so no credentials belong in them. It has no
Secret API rights, source write privileges or global binding. Only the sidecar
mounts a short-lived projected API token; only Nginx mounts the TLS private key.
Both containers are non-root, have read-only root filesystems and drop capabilities.
The sidecar owns `0640` files; making them owner-read-only breaks future updates.
An empty folder-annotation setting disables upstream per-ConfigMap folder overrides.

The policy label is a selection mechanism, not a security boundary. Restrict
ConfigMap writers in this namespace to the reviewed Operator/administrators.
The generic sidecar supports binary and `.url` keys; do not let untrusted writers
supply labeled ConfigMaps or arbitrary keys/annotations. The Operator emits only
one controlled `.rego` key. Do not reuse this authority for tenant configuration.

## Installation boundary

The existing default/production/Operator kustomizations do not reference this
directory. Before an explicit installation:

1. Provide `aep-system/aep-access-policy-tls` through the deployment Secret
   system. It must contain `tls.crt` and `tls.key`, with a certificate valid
   for the chosen service name (for example `aep-access-policy-source.aep-system.svc`).
   No certificate private material is checked in or generated by this deployment.
2. Arrange a trusted CA bundle in every Authorino container. Go's normal TLS
   validation must trust this service chain and verify its hostname. If an
   internal CA is used, mount a reviewed full bundle and set `SSL_CERT_FILE`;
   preserve the public roots needed for issuer/JWKS verification. Never disable
   certificate checks. This stage does not deploy Authorino or its CA overlay.
3. Use a CNI enforcing Kubernetes NetworkPolicy. The source accepts only same-
   namespace Pods labeled `gateway.aep.zhiyuan.io/policy-reader=true` on 8443.
   Protect that label and namespace's Pod creation rights. Existing broader
   policies are additive and can widen access; inspect them before installation.
4. Permit the watcher to reach the Kubernetes API under the site's egress
   policy. This manifest does not add a broad outbound allow rule or expose a
   NodePort/Ingress. API tokens and CA verification remain native Kubernetes.

Render and explicitly install the optional component:

```sh
kubectl kustomize deploy/kubernetes/access-policy-source
kubectl apply -k deploy/kubernetes/access-policy-source
kubectl -n aep-system rollout status deployment/aep-access-policy-source
```

Configure the separately reviewed Operator with
`AEP_GATEWAY_ACCESS_POLICY_BASE_URL=https://aep-access-policy-source.aep-system.svc`.
Source installation alone does not enable the access controller. Its writer
RBAC and native AuthConfig CRD installation remain separate opt-ins.

There are two independently watching source replicas and a disruption budget.
The sidecar's native health endpoint gates initial sync and API/watch freshness;
it is a readiness/startup probe, not a liveness probe tied to downstream API
availability. Dead watcher threads cause the upstream process to exit. Nginx
has separate process health probes. Pod readiness does not prove a particular
file generation or Authorino process has adopted it.

TLS Secret projection does not itself reload Nginx's certificate. The deployment
system must roll the source after a verified certificate rotation and monitor
certificate expiry. `kubectl -n aep-system rollout restart deployment/aep-access-policy-source`
retains availability under the normal two-replica rollout. This is an explicit
operational requirement, not automatic certificate-rotation acceptance.

## Failure semantics and verification

New, changed and deleted labeled ConfigMaps are delivered by a native watch;
adding a binding does not require a new volume mount or Pod rollout. Source
restarts rebuild emptyDir from current ConfigMaps. A 64 MiB per-Pod policy
volume and explicit container memory limits bound the small baseline; measure
the intended grant count/file sizes before scaling.

The upstream sidecar writes files in place rather than atomically renaming.
A reader can briefly receive incomplete content during an update. Authorino
must retain its last successfully compiled module on fetch/compile failure,
and the Operator's uncached absolute validity boundary must still expire it.
No source retry, healthy Pod or cached module may prolong an old publication.
Independent source replicas can temporarily serve different generations;
there is no linearizable publication barrier here. All-serving-process
observation, failure/recovery and complete DB→native runtime acceptance remain
separate gates, with `adoptionGate=false`.

The explicit test creates and cleans only its own fresh Kind cluster. It uses
the actual rendered manifests, fixed upstream containers, disposable CA/server
certificates and strict TLS clients. It checks both replicas for dynamic file
creation/update/deletion, read-only privilege boundaries, denied methods and
paths, and restart recovery. Default Kind does not enforce NetworkPolicy, so
this run explicitly does **not** claim network-policy enforcement. It does not
install a business DB, Higress, Authorino or an employee runtime.

```powershell
$env:KIND = 'path/to/kind'
$env:OPENSSL = 'path/to/openssl'
$env:AEP_POLICY_SOURCE_REPORT = 'path/outside/repository/report.json'
node tests/e2e/access-policy-source.mjs
```

Cache the two fixed container tags and the script's fixed Kind node image in
Docker first. The test preserves the original OCI index/digest while importing
the linux/amd64 platform; it does not replace pinned references with mutable tags.
Generated private material and image archives stay in the owned temporary
directory and are removed in `finally`. Reports contain no credentials.
